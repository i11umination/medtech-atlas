# 用户需求收集与内容动态更新方案（审批稿）

> 历史方案文档：其中“审核”指提交队列管理；正式内容的当前发布门槛以 R1 来源核验流程为准，不要求独立医学专家签署。

状态：历史方案；前台与接口代码已保留，用户于 2026-09-14 决定暂缓接通和部署

日期：2026-09-12

当前约束：未经用户重新确认，不创建或连接 Cloudflare D1，不配置 Pages Binding，不建设审核后台，也不把用户需求系统纳入当前阶段验收。

## 一、建议先明确的边界

用户提交的是“希望网站补充什么”，不是直接发布一条医学结论。建议将流程拆成：

```text
用户提出需求
    ↓
系统做主题归类与重复提示
    ↓
进入待处理队列
    ↓
人工检索、证据提取和医学审核
    ↓
形成节点、关系、证据卡和未来方向
    ↓
审核通过后更新公开图谱
```

系统可以自动完成需求收集、去重、分类、优先级排序和状态通知，但不应自动把用户文字变成“疗法有效”“适合某患者”等公开结论。

## 二、三种可行方案

### 方案 A：静态站点 + GitHub 需求池

技术栈：Astro 静态站点 + GitHub Issue Form/Discussions + GitHub Actions。

实现方式：网站的“提交需求”入口打开预填充的 GitHub 需求表单，需求以 Issue 或 Discussion 进入公开队列；维护者通过标签区分“待归类、检索中、待审核、已纳入、暂不处理”，审核通过后修改 JSON/Markdown 并触发静态构建。

优点：

- 基础设施成本最低，几乎不需要新增数据库；
- 每条需求、讨论、修改和发布记录天然可追溯；
- 内容继续以 JSON/Markdown 和版本控制为中心，符合当前项目结构；
- GitHub Actions 可以在代码变更后自动构建和部署。

缺点：

- 普通公众需要离开网站，且可能需要 GitHub 账号；
- 需求提交体验不够统一；
- 无法在网站内方便地提供提交状态查询；
- 不适合未来大量匿名用户提交。

适用场景：项目早期、提交量很小、维护者熟悉 GitHub、优先保证可追溯性。

### 方案 B：Cloudflare 动态需求箱 + 静态内容发布流水线（推荐）

技术栈：Astro 静态站点 + Cloudflare Pages Functions + Cloudflare D1 + GitHub Actions；后续可选 Cloudflare Turnstile 防垃圾提交。

实现方式：新增与“首页”“图谱探索”并列的“提交需求”入口。用户在站内提交“想了解的疾病/临床问题/科学门类/技术/研究方向”和自然语言描述，Pages Function 接收请求并写入 D1 的 `content_requests` 表。公开站点仍保持静态生成；维护者在受保护的审核入口处理队列，审核通过后将正式内容写入 JSON/Markdown，GitHub Actions 自动执行校验、构建和发布。

推荐的数据状态：

```text
submitted → classified → queued → researching → medical-review → published
                                      ↘ duplicate / rejected / needs-clarification
```

优点：

- 用户全程留在网站内，适合普通公众和科研人员；
- 需求收集是真正动态的，公开知识库仍由审核后的静态内容组成；
- D1 是托管的无服务器 SQL 数据库，可与 Pages Functions 绑定；
- 不需要长期运行的专用服务器，首版可以在免费额度内起步；
- 未来可以增加需求热度、重复合并、主题优先级和状态查询；
- 保留现有 Astro 内容页与 JSON/Markdown，不必立刻把全部知识库迁移到数据库。

缺点：

- 需要 Cloudflare 账号、部署配置和一个受保护的管理员入口；
- 如果希望“审核后自动产生完整内容”，还需要额外的内容编辑界面或 GitHub App；
- 对 Cloudflare 生态有一定绑定；
- 免费额度和平台政策可能变化，需要记录实际用量。

适用场景：希望站内收集需求、逐步扩大内容库，同时保持医学内容人工审核和静态页面性能。

### 方案 C：Supabase 数据库驱动的实时内容库

技术栈：Astro SSR + Cloudflare/Node 适配器 + Supabase Postgres + Supabase Auth + Row Level Security + Supabase Edge Functions；叙事内容可放在数据库或 Storage。

实现方式：用户需求、节点、关系、证据和审核状态都存入 Supabase。用户提交后写入需求表；管理员通过 Auth 登录审核和编辑内容；只有 `published` 状态的数据才能被公开查询，审核通过后页面按请求实时读取最新内容。

优点：

- 审核通过后可以即时更新，不必等待完整静态构建；
- 适合未来大量节点、关系、标签、状态和筛选查询；
- Postgres 适合复杂查询和后续统计；
- RLS 可以在数据库层限制匿名用户与管理员权限；
- Supabase Edge Functions 可承载表单接口、Webhook 和后台逻辑。

缺点：

- 架构复杂度和长期维护成本最高；
- 需要设计迁移、备份、审核版本、来源快照和回滚机制；
- 全部知识内容进入数据库后，当前 JSON/Markdown 的审阅体验会被削弱；
- SSR、登录和数据库权限配置会增加部署与安全负担；
- 仍需自行设计医学内容编辑器和审核工作流。

适用场景：已经有稳定的内容维护团队，预计很快进入大规模、多作者、频繁更新阶段。

## 三、三种方案对比

| 维度 | 方案 A | 方案 B（推荐） | 方案 C |
| --- | --- | --- | --- |
| 站内提交体验 | 弱 | 强 | 强 |
| 需求收集动态性 | 弱 | 强 | 强 |
| 审核后内容更新 | 手工构建 | 审核后自动构建 | 可即时读取 |
| 医学安全可控性 | 很强 | 很强 | 强，但权限设计更复杂 |
| 首版新增复杂度 | 最低 | 中等 | 最高 |
| 与现有 JSON/Markdown 兼容 | 很好 | 很好 | 需要逐步迁移 |
| 普通公众友好度 | 较低 | 高 | 高 |
| 大型内容库潜力 | 中等 | 高 | 很高 |
| 免费起步可行性 | 高 | 较高 | 较高，但受服务额度限制 |

## 四、我的建议

建议选择方案 B，并采用“两层动态”设计：

1. 用户需求队列动态写入 D1，需求提交后立即进入分类和审核流程；
2. 正式医学内容仍由人工研究和审核后写入版本化 JSON/Markdown；
3. GitHub Actions 自动完成 Schema 校验、引用检查、静态构建和发布；
4. 未来当内容规模、维护者和更新频率达到阈值，再把已审核内容逐步迁移到方案 C，而不是一开始就让数据库承担全部知识库。

首版“提交需求”表单建议只收集：需求类型、自然语言描述、希望看到的内容深度、可选的来源线索和反垃圾校验；不收集姓名、联系方式、病历、症状细节或其他不必要的个人健康信息。

## 五、需要用户审批的事项

- 选择方案 A、B 或 C；
- 是否允许提交者在提交后通过一个随机编号查询处理状态；
- 是否允许其他用户看到“大家正在请求的主题”统计；
- 需求是否默认匿名提交；
- 审核通过后的内容是否自动发布，还是进入二次人工发布确认。

本方案不接入 AI 服务；第一版新增入口、需求表单、Cloudflare Pages Function、D1 迁移和构建校验工作流。Cloudflare 账号、D1 数据库 ID 与部署密钥由部署阶段配置，不写入项目文件。
